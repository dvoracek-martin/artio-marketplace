# Security model

## Trust boundaries

- Anonymous users can read eligible published catalog entries and public OCI artifacts only. Publisher, admin, revocation, Zot publisher, and Zot promoter credentials are distinct. A publisher stages artifacts but cannot approve a release or write to the public OCI namespace. The separate admin approves the exact manifest and catalog hashes; Marketplace then uses the promoter credential to copy the approved immutable OCI bundle. The service refuses duplicate configured API token hashes. Raw API tokens are not stored in PostgreSQL.
- Zot ACLs allow the publisher and promoter to access private `staging/**`, grant anonymous read but promoter-only writes to `public/**`, and default-deny other repositories. The promoter is server-side only and is stored outside source control; the read-only htpasswd mount contains separate bcrypt entries. Anonymous staging reads and publisher-to-public writes are tested through both registry gateway listeners.
- Plugin manifests are parsed against the pinned Core v1 Java contract and checked against one operator-configured public registry host and repository prefixes. Before publication, each canonical public digest is mapped to its corresponding private staging repository and independently verified. Promotion copies nested OCI indexes, platform manifests, configs, and layers, then verifies public manifest digests before finalizing catalog visibility.
- All manifest/catalog text is scanned without rewriting the canonical Core manifest; markup, unsafe schemes, controls, excessive depth/value counts and oversized text are rejected. External links require HTTPS. Uploaded media is format-sniffed, decoded, bounded by size/pixels, content-addressed, and hash-checked on read.
- PostgreSQL stores public listing data, release state, media metadata, and an append-style audit log. Published release content is immutable at database layer.
- Marketplace API requests have bounded in-process fixed-window limits (120 public and 30 publisher requests per client per minute by default), global public/publisher admission ceilings, bounded client-bucket memory with expiry/LRU eviction, and a standard `429` response with `Retry-After`. Forwarded client addresses are honored only for exact/CIDR trusted proxy hops and are parsed right to left; the sample ingress overwrites inbound XFF.
- Tomcat bounds request headers, form bodies, connection wait, keep-alive time and request read size. The external HTTPS proxy must additionally enforce request/body deadlines and the configured media request-size boundary.

## Deployment requirements

Use TLS at a managed reverse proxy for non-local access, restrict network paths, protect secrets in an orchestrator secret store, patch the host/runtime, review pinned image digests, apply rate and body-size limits, and monitor authentication failures and disk usage. Local Compose ports are loopback-only and its HTTP registry is for development. Never publish publisher bearer credentials in arguments, CI logs, scripts, or plugin packages.

Publisher, admin, and revocation tokens are separate shared operator credentials, not an identity system; there is no per-person identity or self-service account management. Protect and rotate each credential independently. Use independent people or controlled systems for staging and approval; the credential split alone is not human identity proof. The reverse-proxy example restricts the entire admin API to an operator subnet. Public catalog visibility requires an ACTIVE plugin and a PUBLISHED eligible release. Do not grant anonymous Zot access to private repositories.

## Known scope limits

There is no backoffice UI, payment, or licensing system. Marketplace signs immutable release descriptors and Core verifies those signatures; this does not establish image build provenance, and Core does not validate installed dependency state at Marketplace publication time. Marketplace also publishes a separately signed support/security advisory feed, but Core-side polling, durable verification state and local ban enforcement are still open. Release revocation cannot directly notify a customer Core or disable an installed plugin; there is no remote Core control channel. Core's pinned source maps versioned `/api/v1/admin/extensions/**` requests through its API versioning filter; see [compatibility notes](CORE_COMPATIBILITY.md).

## Temporary upstream vulnerability exceptions (review by 2026-10-30)

The 2026-10-15 Trivy scan found patched Jackson 2/3 and Tomcat dependencies in the Boot 4.1.1 BOM. Marketplace pins safe patched versions (Jackson 2.21.7, Jackson annotations 2.22, Jackson 3.2.3 and Tomcat 11.0.25) using Gradle resolution rules; the Boot plugin and approved Spring Boot line remain unchanged. Jackson annotations 2.22 supplies `@JsonApplyView`, which Jackson 3.2 requires.

The same scan found three CRITICAL Tomcat findings and five HIGH Go findings in Zot. CVE-2026-65182 has a Tomcat fix and is not excepted. CVE-2026-65905 and CVE-2026-68525 had no fixed Tomcat version in the scan database. Zot is pinned to the latest upstream v2.1.21 image digest (`sha256:6b69512c00dceaad05b1144e6079aac6aa7309d7fd200f9947ecb1de09cf48c8`); that release contains Go 1.26.8, `golang.org/x/net` v0.58.0 and gRPC v1.83.1, while fixes require newer components and no later upstream Zot release was available during review. Exact CVE IDs have an expiring `.trivyignore` entry through 2026-10-30; these are accepted, time-bounded upstream risks, not false-positive or non-exploitability claims. Keep Zot behind TLS, enforce its anonymous-read/publisher-write ACL, restrict publisher ingress, and reevaluate the upstream release before the exception expires. The CI scan still fails any other HIGH/CRITICAL finding.
